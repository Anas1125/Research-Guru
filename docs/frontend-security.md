# Frontend security rollout

Static Pages responses receive generated dist/_headers. The Pages Functions middleware applies the same headers to dynamic sitemap and article responses; existing SEO/noindex headers remain intact. CSP defaults to report-only, with no remote reporting endpoint; inspect browser DevTools Console for violations. Other security headers are active immediately.

The policy permits scripts only from the frontend, disallows eval, frames, plugins and workers, and limits fetch/XHR to the frontend and configured HTTPS API origin. Inline CSS remains allowed for dynamic React background styles. HTTPS images, data and blob images are allowed because admin-managed content supports external image URLs and local previews. Narrow this image policy later if the business restricts image hosting. The policy is not a substitute for backend authorization or sanitization.

Cloudflare Pages production VITE_API_URL must be the bare HTTPS backend origin, available both at build and runtime. Leave VITE_CSP_ENFORCE unset or false during testing. Verify headers on /, /admin/login/ and /sitemap.xml, and check a direct published article or a missing article. Test public navigation, enquiry and review submission using authorized test data, admin login/logout, image upload/preview, settings, blog and offers. Review CSP messages separately from unrelated console errors. When satisfied set VITE_CSP_ENFORCE=true in both build and runtime settings and redeploy the latest main. Verify the enforced header and repeat browser checks. Roll back by setting false and redeploying. Never allow unsafe-inline or unsafe-eval in script-src just to silence violations.
